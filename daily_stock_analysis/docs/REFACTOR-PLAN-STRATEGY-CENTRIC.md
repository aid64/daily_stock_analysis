## 二、v5.0 核心判断

三轮审视（v4.1 的 14 条外部批评、v4.2 的 5 条执行审视、本次核实）收敛到同一结论：

> **建设已超前于使用。** 系统能产出结构良好、理由清晰、数量合理的建议，但唯一用户连续 19 天零执行。再给"没人执行的建议"加任何功能，都是第四轮犯同一个错误。

更深的根因（v2.0 审计#1 提出，至今未闭环）：**系统每日执行的规则没有一条经过用户确认**——结构锚价位是脚本生成的、35% 集中度是行业默认、E2 门是实验性分位。人不会执行自己没有同意过的纪律。09-24 单说"卖出 002475 100 股（集中度修复）"，但用户从未同意过"要降到 35%"这件事本身。

v5.0 因此把计划的中心从"建议的正确性"整体移到：
1. **意图的确认**——每条规则要么被用户签署，要么明确标注未确认；
2. **执行的发生**——执行漏斗可见，断在哪一步有数据；
3. **节奏的自律**——无回应的建议自动休眠，不再日复一日重复（"你又说了又说"的根因治理）。

**一个诚实的可能性必须写进计划**：如果 U0 确认后用户停用了大部分规则，"今日无待办"将成为**正确输出而非失败**。系统的价值是执行用户同意的纪律，不是每天生成订单。

## 三、U 系列阶段

### U0：意图归化（一切之前）
系统与用户的一次性对齐——把"默认规则"变成"签署的纪律"。
- **交付形态（2026-09-26 调研后修订：文本命令，非卡片按钮）**：`/规则确认` 命令逐条送审——每条 active 规则（四档价位 / 集中度 35% / E2 门 / 打新 / 逆回购）列"当前在用它做什么、依据、验证状态、当前确认状态"，用户以文本回应：`/规则确认 <编号> 确认|停用 [备注]`。按钮形态（确认/修改/停用三键）**随 U1 的卡片回调基础设施一并升级**——同一套设施服务 U0+U1 两个阶段，不为 U0 单独建一次。
- **形态决策依据（lark-oapi 实测，GitHub/官方 SDK 调研）**：卡片按钮长连接回调技术上可行（本机 SDK 1.7.1 的 Builder 已含 `register_p2_card_action_trigger`，WS 通道原生路由 `card.action.trigger`，无需公网、无需升级依赖），但需在飞书开发者后台**手工订阅**该事件——漏配即完全静默（卡片能发、点击无反应、无日志，社区实践反复踩坑），且无法用代码自证配置到位。U0 的价值在"用户回应"本身，第一波用零依赖、可单测、无静默失败的文本通道；等 U1 建按钮设施时升级，后台配置的坑也只踩一次。
- **确认台账（修订）**：确认记录写**旁路 JSONL**（`data/rule_confirmations.jsonl`，追加式：at/rule_id/action/note/source）——**不重写 `strategies.yaml`**（现有 yaml 写回实现会抹掉全部行内注释）。前置：规则清单先落成代码内清单（5 族规则各附真源位置——集中度 35% 在 .env、E2 门在 quant 产物、价位锚在 .env 规则段；`strategies.yaml` 的 `params_source` 字段代码不解析，注册表里只有策略身份）。
- 未确认期间的行为：建议照常产出，但决策包依据披露标注"规则未确认"，并给确认入口；确认/停用即时生效。
- 验收：每条 active 规则在旁路台账中有明确的 confirmed/disabled 状态与时间戳；决策包依据披露引用该状态而非"系统登记"。
- 回滚：确认是旁路元数据，可撤销；命令可下线，不影响任何建议产出路径。

### U1：执行漏斗仪表
把"为什么零执行"从猜测变成数据。
- **漏斗定义（2026-09-26 修订）**：**送达 → 回应（文本命令先行，后升级卡片按钮）→ 回填**。"已读（飞书回执/表情回应）"层**砍除**——SDK 虽原生支持 reaction/已读事件（本机 1.7.1 channel.py 实测），但需新增 scope 与后台订阅，成本最高、信息量最低（已读 ≠ 会回应，对"零执行"诊断无增量）。
- **第一步（前置小任务）**：发送侧留存 message_id——`feishu_sender._app_send_raw` 成功后把 message_id + logical_id + sent_at 落 JSONL（现状：发送成功即丢弃返回值，这是漏斗无法关联的根因）。
- **建议实例 ID**：logical_id 是"业务身份、同 ID 刷新替换"语义，不能当实例主键——每次建议派生 `logical_id@<date>` 形态的实例 ID 用于漏斗计数与关联。
- **边界（诚实声明）**：策略类建议（逆回购/打新）不进操作单、无可回填对象——它们的漏斗止步"回应"层；操作单买卖腿可走满全程（回填已有 sheet_id + trade_uid 幂等键）。
- 验收：任意一条操作单建议能回答"到了漏斗哪一步"；回应/回填按实例 ID 关联。
- 回滚：纯增强。

### U2：建议休眠与节奏自适应
- 同一规则的同一建议连续 **N 次（建议 N=3）无任何回应** → 系统发一次"继续提醒还是停用该规则？"的确认询问，之后该规则建议进入静默（只在 /操作单 里可见，不进每日待办）。
- **计数源（2026-09-26 修订）**：出站次数（bus 按**实例 ID** 归组，见 U1）− 回应次数（U1 回应存储）。不能用 logical_id 直接计数（刷新替换语义会漏计），更不能用进程内噪声冷却状态（process-local，重启即丢）。
- 静默落点：复用 `strategy_intake.set_registry_status` 幂等状态机（autostop 已打通 dormant 先例），**不新造机制**。
- 与 U0 联动：休眠中的规则在 U0 台账里显示为"待重新确认"。
- 验收：构造连续无回应场景，第 N+1 天起待办区不再出现该建议，只出现一次确认询问。
- 回滚：N 与开关进配置。

## 四、顺序与依赖

```
第一波（现有设施内，零新基础设施）：
  U4（提交周六bug修复+重启 server+备份任务 powershell 包装）
    → U0 文本命令版（/规则确认 + 旁路台账）

第二波（U0 跑通后）：U1 漏斗（回应命令+聚合查询）→ U2 休眠；
  卡片按钮形态随第二波的卡片回调设施一并建设（届时 U0 卡片升级为按钮，后台订阅只配一次）
U3（后台线，等外部产物）   U5（随行）
```
- **无外部 block**：U0 的确认请求本身就是与用户的交互；用户不回应本身就是 U2 的输入。这是 v4.x 各版"依赖用户输入"悬空问题的解法——把用户输入设计成系统的第一等输入，而不是前置条件。
- U1 依赖 U0 建立的**规则清单与用户回应通道**（第一波的文本命令即是）；按钮回调设施在第二波建设，避免为 U0 单独建一次。
